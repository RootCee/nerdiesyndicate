## Rollback and partial-deployment recovery

- Frontend rollback: use Vercel Instant Rollback to deployment
  `dpl_2EKvNMToo4pzxPmwAmFoG86Tx6hj`, or, from the authenticated linked project,
  run:

  ```sh
  vercel rollback dpl_2EKvNMToo4pzxPmwAmFoG86Tx6hj
  ```

- Worker rollback: from the authenticated Cloudflare account, run:

  ```sh
  cd /Volumes/T7/NerdieBlaq/NerdieCity-MafiaWars/source/multiplayer
  npx wrangler rollback 55ed4286-c4dd-4180-9552-3f7ce2cfeae6 \
    --name nerdie-city-multiplayer-v4
  ```

- If the Worker deploy succeeds but the frontend release does not, immediately
  roll the Worker back to the known previous version and verify `/health`.
- If the frontend deploy succeeds but the Worker deploy fails, roll the frontend
  back first; do not leave the new client live against an unverified backend.
- If both deploy but the smoke test fails, roll back the frontend, then the
  Worker, and verify both restored versions. Existing Durable Object records are
  retained; rollback does not delete room data. During Worker rollback, rooms
  created under the 20-player release may remain present but the prior six-player
  admission limit applies.
- Do not run `wrangler delete`, remove Durable Object namespaces, or change
  migration history as a rollback method.
